FINAL_CHECKOUT_SECURITY_FIX_REPORT

A. Root Cause Checkout Failure
When an authenticated web user checks out, the frontend sends their MongoDB _id (a 24-character hex string) as the userId. However, the Order.userId schema explicitly requires a Number (designed originally for Telegram numeric IDs). This type mismatch causes a Mongoose CastError: Cast to Number failed for value....

B. Order.userId Data Flow
FE Auth Session -> User._id (String) -> POST /api/orders -> Order.create(userId: String) -> CastError.

C. Guest Checkout Analysis
Guest checkouts send isGuest: true. The fix bypasses the String/ObjectId mapping for guests and safely sets userId to 
ull, correctly retaining existing guest semantics without forcing a faux numeric ID or causing schema errors.

D. Authenticated Web Checkout Analysis
For authenticated web users, the fix intercepts the 24-character string payload, queries the User collection via User.findById(), and extracts the schema-defined numeric userId. It then passes this numeric ID to Order.create(), resolving the CastError perfectly while maintaining accurate user association. Legacy Telegram numeric IDs simply passthrough unchanged.

E. Payment Gateway Secret Exposure Root Cause
The public endpoint GET /api/settings/payment-gateway returned the entire PaymentGatewaySetting documents directly from MongoDB without stripping sensitive data. This exposed the settings object containing plain-text API keys, merchant IDs, and tokens for TokoPay, KazePay, KitaQris, and OrderKuota to any visitor or browser network inspector. Furthermore, POST /api/settings/payment-gateway lacked authentication, allowing anyone to modify these keys. Lastly, hardcoded fallback API keys were present in the source code of e/index.js.
